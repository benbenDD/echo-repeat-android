# Echo English v1.7.10 Playback Recovery and Sleep Timer Design

## Background

Version 1.7.9 persists the last playback session and restores it on a normal cold start. Device logs nevertheless confirmed two remaining failures:

1. MIUI or Android can remove `PlaybackService` while the activity or its `MainViewModel` still retains the selected track. Pressing play then starts a new service with only `ACTION_TOGGLE`. The new service has no URI, segments, or prepared media item, so playback does nothing and the published progress appears to reset to zero. Selecting the track again works because that path sends a complete `ACTION_LOAD`.
2. A sleep timer configured for "stop at current segment end" reaches the boundary and calls `stopForSleepTimer()`, but ExoPlayer can subsequently publish `STATE_ENDED`. The existing listener treats that as an ordinary segment boundary and starts the next repeat, so the timer appears not to stop.

The v1.7.10 release is a focused patch based on v1.7.9. It does not redesign segment generation, repeat timing, subtitle timing, navigation, or the user interface.

## Goals

- Never create an empty playback service from a non-load command.
- If a selected track exists but the service or its prepared source has disappeared, restore the full source and the saved playback position before accepting playback commands.
- Pressing play in that recovered state starts the selected track immediately from the persisted position.
- Returning to the foreground rehydrates a missing player in the paused state, without unexpectedly starting audio.
- A sleep-timer stop blocks every automatic repeat, gap, segment transition, and playlist advance until the user explicitly presses play.
- Preserve all published v1.7.9 tags, APKs, source archives, and delivery files.
- Publish the patch as version name `1.7.10` and version code `19`.

## Non-goals

- No changes to fixed-length or subtitle segment boundaries.
- No changes to repeat-content accuracy or adjacent-segment playback.
- No automatic playback after a process-level cold start or an ordinary foreground restore.
- No database migration or dependency upgrade.
- No replacement or deletion of earlier delivery artifacts.

## Considered Approaches

### A. Recover in `MainViewModel` before command dispatch (recommended)

Expose whether the live service has a prepared source, then let `MainViewModel` rebuild a complete `ACTION_LOAD` from the selected track, current settings, generated segments, and persisted session when the source is missing. Non-load commands are never allowed to create a new empty service.

This keeps database, subtitle parsing, settings, and segment construction in the existing owner. It is a small change and can be covered with pure policy tests plus existing restore tests.

### B. Make `PlaybackService` reconstruct a track after any command

The service could query Room, DataStore, subtitles, and settings when it receives `ACTION_TOGGLE` without a source. This centralizes recovery but duplicates `MainViewModel` preparation logic, couples the service to more application state, and increases the risk of inconsistent segment construction.

### C. Always reload the selected track before every command

This is simple but would reprepare ExoPlayer unnecessarily, produce audible interruptions, reset repeat state, and increase foreground-service churn. It is rejected.

## Detailed Design

### Playback source health

`PlaybackService` will expose an in-process source status that distinguishes:

- no active service;
- active service without a prepared source;
- active service with a prepared source for a specific media ID.

A source is considered prepared only when the service has a non-null source URI, non-empty segment arrays, and at least one player media item. A stale `PlaybackBus` snapshot alone is never proof that the source is available.

### Command delivery policy

`MainViewModel` will use a pure command-recovery policy with these outcomes:

| Situation | Outcome |
|---|---|
| Full `ACTION_LOAD` | Start or dispatch normally |
| Non-load command and matching source is ready | Dispatch to the active service |
| Play/toggle and source is missing but a selected track exists | Rebuild full load from the persisted session with `autoPlay=true` |
| Foreground resume and source is missing but a selected track exists | Rebuild full load from the persisted session with `autoPlay=false` |
| Seek or segment navigation and source is missing | Rebuild paused at the requested target instead of starting an empty service |
| Settings-update command and source is missing | Do not create a service; saved settings are included in the next full load |
| Non-load command with no selected track | Ignore safely and show no false playback state |

Recovery preserves the persisted absolute position, segment index, and repeat index when valid. Explicit play clears a previous sleep-timer stop through the normal load/play path. Foreground recovery must never autoplay.

The command path must be serialized in the `MainViewModel` coroutine scope so two rapid taps cannot start two competing loads.

### Foreground recovery

`MainActivity` will notify `MainViewModel` from `onResume()`. If the current track is already prepared in the active service, no work occurs. If a current track exists but the source is missing, the view model performs a paused full load from the persisted session. Initial startup remains owned by the existing `restoreStartup()` path; a guard prevents duplicate startup and resume loads.

### Sleep-timer terminal state

`stopForSleepTimer()` will set `stopReason=SLEEP_TIMER` before pausing the player, then cancel boundary messages, repeat timing, gap callbacks, and pending transition state. This ordering makes the stop reason visible even if a player callback arrives immediately.

Both automatic entry points must reject work while `stopReason` is `SLEEP_TIMER`:

1. the `STATE_ENDED` listener must not call `handlePlaybackWindowEnded()`;
2. `handlePlaybackWindowEnded()` must return before changing segment/repeat state, providing defense in depth against a delayed callback.

Only an explicit user play/toggle or a new full track load clears the sleep stop. Timer cleanup must preserve the stop reason while clearing the deadline preferences.

## Error Handling

- If the selected track is missing or no longer readable, recovery does not start a service and shows the existing unavailable-track message.
- If Android rejects a foreground-service start, keep the existing user-facing error message and leave the saved session intact for a later retry.
- If persisted indices exceed regenerated segments, clamp them using the existing load behavior.
- Dropped settings commands are not errors because settings are already persisted and will be applied on the next load.

## Test Strategy

### Unit regression tests

- A non-load command cannot request creation of a new empty service.
- Missing source plus play/toggle selects full-load recovery with autoplay.
- Missing source plus foreground resume selects full-load recovery paused.
- A matching prepared source dispatches normally without reloading.
- Sleep-timer stop forbids `STATE_ENDED` boundary automation.
- Sleep-timer stop forbids direct playback-window completion handling.
- Natural `STATE_ENDED` without a stop reason still repeats or advances normally.
- Explicit play after a sleep stop is allowed and clears the terminal reason.

Each regression test must be observed failing against v1.7.9 before production code changes.

### Full verification

- Run all debug unit tests and confirm zero failures.
- Compile debug Kotlin and assemble the debug APK with JDK 17.
- Install v1.7.10 over v1.7.9 without clearing application data.
- On the connected Xiaomi device, reproduce a missing-service state using MIUI recent-task cleanup, reopen the app, and verify the selected track and exact saved position are visible while paused.
- Press play and verify it starts without returning to the playlist and without resetting progress.
- Configure "stop at current segment end", let it expire at a repeat boundary, and verify no repeat, gap, segment change, playlist advance, or delayed restart occurs.
- Press play explicitly afterward and verify playback resumes.
